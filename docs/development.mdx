Run commands from the repository root. Development requires Python 3.13+, uv, Bun, and Docker with Compose.

## Contribution workflow

Before changing code, read the [contributor guide](https://github.com/michel-tricot/airmux/blob/main/CONTRIBUTING.md),
`AGENTS.md`, and the relevant record under `notes/design/`. Add a failing behavior test first, keep the implementation
focused, and update every affected schema, generated client, example, and document in the same change.

Run focused tests while iterating. Before opening a pull request, run the full checks for the areas touched and describe
the user impact, design tradeoffs, and verification in the pull request body. Inference request-path changes require both
the acceptance scenarios and a real request through a running data plane.

## Install and initialize

```bash
uv sync --all-packages --frozen
bun install --frozen-lockfile
uv run pre-commit install
cp .env.example .env
docker compose -f docker-compose.dev.yml up -d --wait
uv run airmux control-plane bootstrap-keygen
uv run airmux control-plane migrate
uv run airmux control-plane taxonomy --file taxonomy/taxonomy.yml
```

Run `bootstrap-keygen` once. It creates `.airmux/dataplane.key`; keep it with the matching local database. This leaves
the instance unclaimed so the normal onboarding flow remains available.

## Start the services

Run each process in a separate terminal:

| Process | Command | Address |
| --- | --- | --- |
| Control plane | `uv run airmux control-plane serve --dev` | `http://127.0.0.1:8000` |
| Data plane | `uv run airmux gateway serve --config airmux.yml --dev` | `http://127.0.0.1:8080` |
| Console | `bun run dev` | `http://127.0.0.1:5000` |

Complete setup through Vite's public development origin:

```bash
uv run --package airmux airmux quickstart --url http://127.0.0.1:5000
```

Vite forwards `/api` and `/inf` to the Python services. Use the same hostname throughout a browser session.

## Gateway-only development

```bash
uv run --package airmux airmux gateway init --taxonomy taxonomy/taxonomy.yml --directory .airmux-gateway
export OPENAI_API_KEY='your-provider-key'
uv run --package airmux airmux gateway serve --config .airmux-gateway/airmux.yml --dev
```

The generated bundle references the existing taxonomy file. Both reload after edits. This mode uses environment provider
keys, a private generated inference key, and a `devnull` usage outbox. See [gateway-only deployment](/docs/deployment/gateway)
for installation without a source checkout at runtime.

The Docker-free subprocess suite progresses through basics, protocol pairs, features, simple policies, advanced policy
composition, failures and fallback, runtime changes, and metering prices and costs. It starts real gateways and scripted
upstream HTTP servers, then validates their JSON Lines usage events against the shared contract:

```bash
uv run pytest tests/acceptance/gateway -n auto
```

PR CI runs the levels in order against the rebuilt, installed public wheel and uploads JUnit results, sanitized
configuration, provider requests, responses, gateway logs, and usage events. Each scenario is independent.
For focused runs and contribution conventions, see the [gateway suite README](https://github.com/michel-tricot/airmux/blob/main/tests/acceptance/gateway/README.md).

CI builds the candidate distributions once on Linux, validates their README metadata, and rebuilds the wheel from the
sdist. Four portable installation jobs install that same wheel with Python 3.13 and 3.14 on `ubuntu-latest` and
`macos-latest`. They have no source checkout and use only pytest, HTTPX, and PyYAML in a separate test environment.
They verify CLI help/version, bundled module locations and interpreter version, starter taxonomy initialization,
real buffered and streaming requests through a local stub upstream, and SIGTERM shutdown. Missing executable paths,
startup failures, and shutdown timeouts fail with diagnostics rather than skipping. This matrix does not cover Windows.
Postgres/Docker installation checks, the full integration suite, and gateway acceptance levels remain Linux-only;
the installation and gateway acceptance jobs reuse the candidate wheel.

The change adds one Linux distribution job and four smoke jobs to each CI run. Each has a ten-minute timeout,
so the added job time is capped at 30 Linux runner minutes and 20 macOS runner minutes before savings from removing
nine repeated distribution builds. These are execution ceilings, not measured usage or billing estimates.
The smoke matrix permits two concurrent jobs, requiring at least two scheduling waves after the distribution job;
runner availability can add queue time. Each smoke job records elapsed runner seconds in its Actions summary;
the Actions job timeline records queue time. Use those measurements to assess cost before expanding the matrix.

To run the portable checks locally without installing the workspace:

```bash
uv tool install --python 3.13 dist/airmux-*.whl
uv venv --python 3.13 /tmp/airmux-smoke-runner
uv pip install --python /tmp/airmux-smoke-runner/bin/python pytest httpx pyyaml
mkdir -p /tmp/airmux-installation-tests
cp tests/installation/{conftest,test_cli,test_gateway}.py /tmp/airmux-installation-tests/
cd /tmp
AIRMUX_INSTALL_BIN="$(command -v airmux)" AIRMUX_INSTALL_PYTHON=3.13 \
  /tmp/airmux-smoke-runner/bin/python -I -m pytest /tmp/airmux-installation-tests
```

## Workflow checks

PR CI has an independent five-minute workflow check. It runs actionlint 1.7.12 with ShellCheck for embedded shell,
verifies inputs against each pinned action's upstream metadata, and checks formatting for every workflow. Install
actionlint and ShellCheck locally, then run:

```bash
actionlint
AIRMUX_VALIDATE_ACTION_INPUTS=1 uv run pytest tests/workflows -q
bunx --no-install prettier --check '.github/workflows/*.{yml,yaml}'
```

The metadata check reads public upstream files at the exact commit pin because actionlint's built-in action input
checks do not cover full SHA references. The required correctness gate includes the workflow check, so invalid workflow
changes cannot pass the merge gate. It also proves that unknown inputs fail; the local diagnostics tests prove
that invalid expressions, malformed YAML, and shell mistakes fail. Dependabot maintains the action SHA pins weekly.

Every workflow defaults to `contents: read`, checkouts discard Git credentials, and only the publishing job gets
`id-token: write`. Artifact uploads and same-run downloads use the Actions runtime token. Provider credentials stay
in the release environment, outside PR CI.

Timeouts allow headroom over successful runs 35048133470 and 35047449782: frontend took 2.4–3.5 minutes, backend
4.7–4.9 minutes, installation under one minute, gateway shards up to 3.5 minutes, aggregation 22 seconds, full-stack
acceptance up to 4.7 minutes, and performance 3.6 minutes. Docker run 35048133515 took under three minutes per variant.
The current release build also runs the entire gateway suite sequentially, so it gets 30 minutes; the previous release
run 34930300106 took 56 seconds to build and 17 seconds to publish before those additional gates. Publishing gets ten
minutes, PyPI verification retains twenty minutes, release announcement gets five minutes, and live-provider acceptance
retains its twenty-minute limit. Reusable workflow callers inherit the callee's job timeout because GitHub does not accept `timeout-minutes` on a calling job. The three required status aggregation
jobs only evaluate dependency results with jq and have one-minute limits.

## Python checks

```bash
uv run ruff format .
uv run ruff check .
uv run ty check .
uv run lint-imports
uv run pytest -n auto
```

Control-plane unit tests do not need Postgres:

```bash
uv run pytest apps/control-plane/tests/unit
```

Integration tests start one throwaway Postgres server and clone a migrated template database per test. Docker must be
running. `AIRMUX_TEST_PG_URL` can point to a disposable long-lived Postgres server whose user may create databases.

Request-path changes also require black-box scenarios and a real request against a running data plane:

```bash
uv run pytest tests/acceptance/full_stack/scenarios
```

## Generated contracts

After changing a management endpoint or canonical schema:

```bash
./scripts/export-openapi.sh
./scripts/generate-api-models.sh
./scripts/export-completion-schemas.sh
bun run --cwd lib/api-spec codegen
```

Commit generated files with their source. Do not edit generated API models, clients, or schemas by hand.

## Reset development state

Stop the three source processes, then run:

```bash
docker compose -f docker-compose.dev.yml down -v
rm -rf .airmux
```

This permanently deletes the development database, runtime key, provider credentials, bundle cache, and usage outbox. Repeat initialization afterward.

## Install a local build

For an unreleased checkout, build the public distribution and install it into an isolated tool environment:

```bash
./scripts/build-python-distribution.sh
uv tool install --reinstall dist/airmux-*.whl
```

The installation includes both runtimes. Invoke `airmux` directly from any directory.

## Publish the Python distribution

The repository publishes one `airmux` distribution containing the CLI, contract, generated API models, and both
runtimes. The separate workspace projects keep local dependency and import boundaries explicit, but are not published.
Dispatch `publish.yml` from `main` with an existing candidate tag and its full 40-character commit SHA:

```bash
gh workflow run publish.yml --ref main -f tag=v0.1.1 -f sha="$(git rev-parse 'v0.1.1^{commit}')"
```

The tag must resolve to that exact SHA, the commit must belong to `main`, and the tag version must match the public
distribution version. The workflow builds one candidate wheel and source distribution, rebuilds the wheel from
the source distribution, and verifies the rebuilt installation and gateway. A required live-provider job installs
the original candidate wheel and verifies OpenAI and Anthropic requests, tools, structured output, policies,
fallback, and metering. Both gates must pass before any upload or GitHub release announcement.

The PyPI publication job uses OIDC only and uploads attestations alongside the original candidate artifacts. Configure
`OPENAI_API_KEY` and `ANTHROPIC_API_KEY` as environment secrets in `release`; missing credentials fail the gate.
Configure the PyPI trusted publisher for `michel-tricot/airmux`, workflow `publish.yml`, and environment
`release` in the [PyPI project publishing settings](https://pypi.org/manage/project/airmux/settings/publishing/).
If `airmux` does not exist on PyPI yet, configure a pending publisher with project name `airmux` in your
[account publishing settings](https://pypi.org/manage/account/publishing/), as described in the
[PyPI first-upload guide](https://docs.pypi.org/trusted-publishers/creating-a-project-through-oidc/).
Verify the project name and all four publisher fields before dispatching a candidate; no stored PyPI token is used.
A successful first upload proves that the renamed workflow can obtain the publishing identity.

After upload, the workflow downloads both artifacts for the exact version from PyPI, compares the registry digests
and downloaded bytes against the tested candidate, and installs the downloaded wheel into a fresh tool environment
without a cache. It checks CLI help and the exact version outside the checkout, then sends a real request through
the installed local gateway to a stub upstream and verifies usage accounting. Only after this succeeds does it
create and publish GitHub release notes identifying the version and source commit. This workflow does not deploy
to production.

If upload succeeds but PyPI verification fails, the package is already public on PyPI, but the GitHub announcement
remains unpublished. Use **Re-run failed jobs** on the original Actions run within the 30-day candidate artifact
retention period. This preserves the exact tested bytes and skips the successful build and live-provider gates.
If the upload job itself failed partway through, its hash-aware `uv publish --check-url` skips identical existing
files and uploads the remaining files; different hashes fail. If announcement fails after draft creation, rerunning
checks its version and source commit before publishing that draft. Do not rebuild and overwrite an uploaded version.
For a defective package or expired candidate artifacts, fix the source and choose a new version and tag.

The same live suite runs nightly on main and can be dispatched manually against an immutable source SHA:

```bash
gh workflow run live-providers.yml --ref main -f ref="$(git rev-parse HEAD)"
```

Manual and scheduled checks build and install a distribution rather than serving the workspace sources.
The live suite does not run on ordinary PRs.
See the [live-provider suite README](https://github.com/michel-tricot/airmux/blob/main/tests/acceptance/live_providers/README.md)
for local execution, request bounds, and model maintenance.

## Run deployment tests

The deployment suite uses a local test provider and a disposable project:

```bash
AIRMUX_PORT=18080 AIRMUX_PUBLIC_URL=http://localhost:18080 \
  docker compose -p airmux-test up -d --build --wait

AIRMUX_PORT=18080 AIRMUX_PUBLIC_URL=http://localhost:18080 \
  DEPLOYMENT_PROJECT=airmux-test \
  DEPLOYMENT_FILE=docker-compose.yml \
  DEPLOYMENT_URL=http://localhost:18080 \
  uv run pytest tests/deployment
```

The suite creates accounts, makes buffered and streaming requests, checks usage export, restarts services, and verifies
persistent state. Use only a disposable installation.
