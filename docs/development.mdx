Run commands from the repository root. Development requires Python 3.13+, uv, Bun, and Docker with Compose.

## Contribution workflow

Before changing code, read the [contributor guide](https://github.com/michel-tricot/tokkeeper/blob/main/CONTRIBUTING.md),
`AGENTS.md`, and the relevant record under `notes/design/`. Add a failing behavior test first, keep the implementation
focused, and update every affected schema, generated client, example, and document in the same change.

Run focused tests while iterating. Before opening a pull request, run the full checks for the areas touched and describe
the user impact, design tradeoffs, and verification in the pull request body. Inference request-path changes require both
the acceptance scenarios and a real request through a running data plane.

## Install and initialize

```bash
uv sync --all-packages --frozen
bun install --frozen-lockfile
uv run pre-commit install
cp .env.example .env
docker compose -f docker-compose.dev.yml up -d --wait
uv run tokkeeper control-plane bootstrap-keygen
uv run tokkeeper control-plane migrate
uv run tokkeeper control-plane taxonomy --file taxonomy/taxonomy.yml
```

Run `bootstrap-keygen` once. It creates `.tokkeeper/dataplane.key`; keep it with the matching local database. This leaves
the instance unclaimed so the normal onboarding flow remains available.

## Start the services

Run each process in a separate terminal:

| Process | Command | Address |
| --- | --- | --- |
| Control plane | `uv run tokkeeper control-plane serve --dev` | `http://127.0.0.1:8000` |
| Data plane | `uv run tokkeeper gateway serve --config tokkeeper.yml --dev` | `http://127.0.0.1:8080` |
| Console | `bun run dev` | `http://127.0.0.1:5000` |

Complete setup through Vite's public development origin:

```bash
uv run --package tokkeeper tokkeeper quickstart --url http://127.0.0.1:5000
```

Vite forwards `/api` and `/inf` to the Python services. Use the same hostname throughout a browser session.

## Gateway-only development

```bash
uv run --package tokkeeper tokkeeper gateway init --taxonomy taxonomy/taxonomy.yml --directory .tokkeeper-gateway
export OPENAI_API_KEY='your-provider-key'
uv run --package tokkeeper tokkeeper gateway serve --config .tokkeeper-gateway/tokkeeper.yml --dev
```

The generated bundle references the existing taxonomy file. Both reload after edits. This mode uses environment provider
keys, a private generated inference key, and a `devnull` usage outbox. See [gateway-only deployment](/docs/deployment/gateway)
for installation without a source checkout at runtime.

The Docker-free subprocess suite progresses through basics, protocol pairs, features, simple policies, advanced policy
composition, failures and fallback, runtime changes, and metering prices and costs. It starts real gateways and scripted
upstream HTTP servers, then validates their JSON Lines usage events against the shared contract:

```bash
uv run pytest tests/acceptance/gateway -n auto
```

PR CI runs the levels in order against the rebuilt, installed public wheel and uploads JUnit results, sanitized
configuration, provider requests, responses, gateway logs, and usage events. Each scenario is independent.
For focused runs and contribution conventions, see the [gateway suite README](https://github.com/michel-tricot/tokkeeper/blob/main/tests/acceptance/gateway/README.md).

## Python checks

```bash
uv run ruff format .
uv run ruff check .
uv run ty check .
uv run lint-imports
uv run pytest -n auto
```

Control-plane unit tests do not need Postgres:

```bash
uv run pytest apps/control-plane/tests/unit
```

Integration tests start one throwaway Postgres server and clone a migrated template database per test. Docker must be
running. `TOKKEEPER_TEST_PG_URL` can point to a disposable long-lived Postgres server whose user may create databases.

Request-path changes also require black-box scenarios and a real request against a running data plane:

```bash
uv run pytest tests/acceptance/full_stack/scenarios
```

## Generated contracts

After changing a management endpoint or canonical schema:

```bash
./scripts/export-openapi.sh
./scripts/generate-api-models.sh
./scripts/export-completion-schemas.sh
bun run --cwd lib/api-spec codegen
```

Commit generated files with their source. Do not edit generated API models, clients, or schemas by hand.

## Reset development state

Stop the three source processes, then run:

```bash
docker compose -f docker-compose.dev.yml down -v
rm -rf .tokkeeper
```

This permanently deletes the development database, runtime key, provider credentials, bundle cache, and usage outbox. Repeat initialization afterward.

## Install a local build

For an unreleased checkout, build the public distribution and install it into an isolated tool environment:

```bash
./scripts/build-python-distribution.sh
uv tool install --reinstall dist/tokkeeper-*.whl
```

The installation includes both runtimes. Invoke `tokkeeper` directly from any directory.

## Publish the Python distribution

The repository publishes one `tokkeeper` distribution containing the CLI, contract, generated API models, and both
runtimes. The separate workspace projects keep local dependency and import boundaries explicit, but are not published.
Publishing a GitHub release with a tag such as `v0.1.0` runs `publish.yml`. The workflow rejects a tag that differs
from the public distribution version, builds one wheel and source distribution, rebuilds the wheel from its source
distribution, and runs the installed behavior suite. A required live-provider job then installs the actual release
wheel and verifies OpenAI and Anthropic requests, tools, structured output, policies, fallback, and metering.
The separate PyPI publication job requires both the build and live-provider jobs to succeed. Configure
`OPENAI_API_KEY` and `ANTHROPIC_API_KEY` as environment secrets in `release`; missing credentials fail the gate.
Configure the PyPI trusted publisher for `michel-tricot/tokkeeper`, workflow `publish.yml`, and environment
`release`. Its environment must match the publication job.

The same live suite runs nightly on main and can be dispatched manually. It does not run on ordinary PRs.
See the [live-provider suite README](https://github.com/michel-tricot/tokkeeper/blob/main/tests/acceptance/live_providers/README.md)
for local execution, request bounds, and model maintenance. The existing trigger starts after GitHub release
metadata is published; these checks gate the package publication to PyPI.

## Run deployment tests

The deployment suite uses a local test provider and a disposable project:

```bash
TOKKEEPER_PORT=18080 TOKKEEPER_PUBLIC_URL=http://localhost:18080 \
  docker compose -p tokkeeper-test up -d --build --wait

TOKKEEPER_PORT=18080 TOKKEEPER_PUBLIC_URL=http://localhost:18080 \
  DEPLOYMENT_PROJECT=tokkeeper-test \
  DEPLOYMENT_FILE=docker-compose.yml \
  DEPLOYMENT_URL=http://localhost:18080 \
  uv run pytest tests/deployment
```

The suite creates accounts, makes buffered and streaming requests, checks usage export, restarts services, and verifies
persistent state. Use only a disposable installation.
