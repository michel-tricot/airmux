`tokkeeper` is the entry point for remote management, the inference gateway, and the control-plane server.
Local runtime commands do not require a saved login profile. Remote resource commands use the authentication context below.

## Installation

From a checkout with Python 3.13+ and uv:

```bash
uv build --all-packages --wheel
uv tool install --find-links dist ./dist/tokkeeper-0.1.0-py3-none-any.whl
```

Choose the extras needed by this machine when installing:

| Wheel requirement                                                | Capabilities                                    |
| ---------------------------------------------------------------- | ----------------------------------------------- |
| `./dist/tokkeeper-0.1.0-py3-none-any.whl`                        | Remote management and diagnostics               |
| `./dist/tokkeeper-0.1.0-py3-none-any.whl[gateway]`               | Remote management and a local inference gateway |
| `./dist/tokkeeper-0.1.0-py3-none-any.whl[control-plane]`         | Remote management and a local control plane     |
| `./dist/tokkeeper-0.1.0-py3-none-any.whl[gateway,control-plane]` | Both local runtimes and remote management       |

Quote a wheel requirement containing brackets in your shell. Add `--reinstall` to change the extras of an existing tool installation.
All TokKeeper packages are versioned together. These commands install locally built wheels; they do not require a published release.

If `tokkeeper` is not on your PATH, run `uv tool update-shell` and restart your shell.
`tokkeeper --version` prints the installed CLI version. Every command's `--help` works without installing its runtime;
running a missing runtime command explains which extra to install.

For development, `uv sync --all-packages` followed by `uv run tokkeeper` uses the checkout.

## Local runtimes

| Group           | Commands                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------------ |
| `gateway`       | `init`, `validate`, `serve`, `schema`                                                                  |
| `control-plane` | `init`, `validate`, `serve`, `migrate`, `bootstrap-keygen`, `owner`, `taxonomy`, `fixtures`, `openapi` |

Configuration resolution is `--config/-c`, then `TOKKEEPER_CONFIG`, then `./tokkeeper.yml`.
Relative runtime paths and `${file:...}` references resolve against their containing configuration file.
`init` defaults to the current directory; `--directory/-d` selects another. It creates private keys, never prints them,
and refuses to overwrite any generated file. `validate` checks local configuration without contacting providers or the database.

For a standalone gateway, follow [Gateway only](/docs/deployment/gateway). For a connected deployment with existing Postgres:

```bash
tokkeeper control-plane init --directory deployment --console-url https://llm.example.com
export DATABASE_URL='postgresql://user:password@localhost:5432/tokkeeper'
tokkeeper control-plane validate --config deployment/tokkeeper.yml
tokkeeper control-plane migrate --config deployment/tokkeeper.yml
tokkeeper control-plane taxonomy --config deployment/tokkeeper.yml --file /path/to/taxonomy.yml
tokkeeper control-plane serve --config deployment/tokkeeper.yml
```

In another terminal, run `tokkeeper gateway serve --config deployment/tokkeeper.yml`. The generated configuration shares a
private bootstrap key and file secret store between the planes. The gateway extra must also be installed on that machine.
The control plane defaults to `127.0.0.1:8000` and the gateway to `127.0.0.1:8080`; use `--host` and `--port` to change them.
The console and public reverse proxy are deployed separately. `--console-url` names their public origin; it does not start a console.

`serve` runs in the foreground. It does not create accounts or import a taxonomy. Control-plane migrations are explicit;
`control-plane serve --dev` applies them before starting the development reloader. `gateway serve --dev` reloads Python code
and cannot be combined with multiple `--workers`. Local taxonomy and bundle reloads work without `--dev`.

`control-plane taxonomy --file` reads its path relative to the configuration file. Top-level `taxonomy apply` instead uses
the authenticated management API. `control-plane owner` is local recovery through database access; it promotes an existing
human account. `control-plane fixtures` is for development databases without human accounts and prints access details through
`--format table|json|text`.

Containers invoke these same runtime commands. Update containers by replacing the image; the CLI never updates packages
inside a running container.

## Authentication and context

`tokkeeper login` uses a browser device flow and saves a private profile to `~/.tokkeeper/config.toml`. Override the file with `TOKKEEPER_CLI_CONFIG`.

```bash
tokkeeper login --url https://llm.example.com
tokkeeper profiles list
tokkeeper profiles use my-org
tokkeeper workspaces use production
tokkeeper status
tokkeeper doctor
```

Resolution order is explicit option, `--dev` where supported, environment, active profile, then local default.

| Environment variable          | Purpose                                           |
| ----------------------------- | ------------------------------------------------- |
| `TOKKEEPER_CONTROL_PLANE_URL` | Override the management origin                    |
| `TOKKEEPER_GATEWAY_URL`       | Override the inference origin used by diagnostics |
| `TOKKEEPER_MANAGEMENT_KEY`    | Override the saved profile token                  |
| `TOKKEEPER_ORG_ID`            | Override the selected organization                |
| `TOKKEEPER_CLI_CONFIG`        | Override the profile file path                    |

## Output formats

Commands returning resource data accept `-f/--format table|json|text`. Table is the interactive default, JSON is
intended for automation, and text is tab-separated.

```bash
tokkeeper models list -f json
tokkeeper events list -f text
tokkeeper commands -f table
```

`tokkeeper commands` is the source-backed inventory for the installed CLI version.

## Setup commands

| Command                                            | Purpose                                                                                                       |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `quickstart`                                       | Claim or resume an instance, create a workspace and inference key, import provider keys, and verify inference |
| `login`                                            | Sign in through the browser device flow                                                                       |
| `status`                                           | Show active endpoints, organization, workspace, and authentication source                                     |
| `doctor`                                           | Check profile permissions, control-plane access, authentication, and gateway readiness                        |
| `profiles list`, `profiles use`, `profiles remove` | Manage saved deployment and organization contexts                                                             |

## Automation pattern

```bash
export TOKKEEPER_CONTROL_PLANE_URL='https://llm.example.com'
export TOKKEEPER_MANAGEMENT_KEY='sk-cp-your-key'
export TOKKEEPER_ORG_ID='your-org-id'

tokkeeper workspaces list -f json
tokkeeper inference-keys create deployment --workspace production
```

Use a service account and a management key limited to the required scope and permissions. One-time secret output should
be captured by a secret manager and not written to logs.
