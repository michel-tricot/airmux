`airmux` is the entry point for remote management, the inference gateway, and the control-plane server.
Local runtime commands do not require a saved login profile. Remote resource commands use the authentication context below.

## Installation

With Python 3.13+ and uv:

```bash
uv tool install airmux
```

The installation includes remote management, the gateway, and the control plane. Installing the package starts no services.
A standalone gateway does not require a running control plane or database.

If `airmux` is not on your PATH, run `uv tool update-shell` and restart your shell.
`airmux --version` prints the installed CLI version. Use `airmux --help` to see all commands.

Install command completion for the current shell with `airmux completion`. Use `--shell` to select
`bash`, `zsh`, `fish`, `powershell`, or `pwsh` instead of detecting it automatically.

For source checkouts and unreleased builds, see [Development](/docs/development).

## Local runtimes

| Group           | Commands                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------------ |
| `gateway`       | `init`, `validate`, `serve`, `schema`                                                                  |
| `control-plane` | `init`, `validate`, `serve`, `migrate`, `bootstrap-keygen`, `owner`, `taxonomy`, `fixtures`, `openapi` |

Configuration resolution is `--config/-c`, then `AIRMUX_CONFIG`, then per-runtime defaults; the
[configuration reference](/docs/reference/configuration) names them.
Relative runtime paths and `${file:...}` references resolve against their containing configuration file.
`gateway init` defaults to `.airmux`; `control-plane init` defaults to the current directory. `--directory/-d` selects another.
Initialization creates private keys, never prints their values, and refuses to overwrite any generated file. `gateway init`
copies the shipped taxonomy by default; `--taxonomy PATH` references an existing file without copying it. It finishes with
copyable start, readiness, and inference commands for a real model from the selected taxonomy, preferring one whose provider
variable is already set. Initialization writes ignore rules for generated keys and runtime secret state. `validate` checks local
configuration without contacting providers or the database.

For a standalone gateway, follow [Gateway only](/docs/deployment/gateway). For a connected deployment with existing Postgres:

```bash
airmux control-plane init --directory deployment --console-url https://llm.example.com
export DATABASE_URL='postgresql://user:password@localhost:5432/airmux'
airmux control-plane validate --config deployment/airmux.yml
airmux control-plane migrate --config deployment/airmux.yml
airmux control-plane taxonomy --config deployment/airmux.yml --file /path/to/taxonomy.yml
airmux control-plane serve --config deployment/airmux.yml
```

In another terminal, run `airmux gateway serve --config deployment/airmux.yml`. The generated configuration shares a
private bootstrap key and file secret store between the planes. The same installation can run both services.
The control plane defaults to `127.0.0.1:8000` and the gateway to `127.0.0.1:8080`; use `--host` and `--port` to change them.
The console and public reverse proxy are deployed separately. `--console-url` names their public origin; it does not start a console.

`serve` runs in the foreground. It does not create accounts or import a taxonomy. Control-plane migrations are explicit;
`control-plane serve --dev` applies them before starting the development reloader. `gateway serve --dev` reloads Python code
and cannot be combined with multiple `--workers`. Local taxonomy and bundle reloads work without `--dev`.

`control-plane taxonomy --file` reads its path relative to the configuration file. Top-level `catalog apply` instead uses
the authenticated management API. `control-plane owner` is local recovery through database access; it promotes an existing
human account. `control-plane fixtures` is for development databases without human accounts and prints access details through
`--format table|json|text`.

Containers invoke these same runtime commands. Update containers by replacing the image; the CLI never updates packages
inside a running container.

## Authentication and context

`airmux login` uses a browser device flow and saves a private profile to `~/.airmux/config.toml`. Override the file with `AIRMUX_CLI_CONFIG`.

```bash
airmux login --url https://llm.example.com
airmux profiles list
airmux profiles use my-org
airmux workspaces use production
airmux status
airmux doctor
```

Resolution order is explicit option, `--dev` where supported, environment, active profile, then local default.

| Environment variable          | Purpose                                           |
| ----------------------------- | ------------------------------------------------- |
| `AIRMUX_CONTROL_PLANE_URL` | Override the management origin                    |
| `AIRMUX_GATEWAY_URL`       | Override the inference origin used by diagnostics |
| `AIRMUX_MANAGEMENT_KEY`    | Override the saved profile token                  |
| `AIRMUX_ORG_ID`            | Override the selected organization                |
| `AIRMUX_CLI_CONFIG`        | Override the profile file path                    |

## Output formats

Commands returning resource data accept `-f/--format table|json|text`. Table is the interactive default, JSON is
intended for automation, and text is tab-separated.

Paginated list commands request 50 results by default. Use `--limit 1..200` to choose the page size and `--all` to follow
cursors until every page has been fetched. Without `--all`, output contains only the first page. Configuration and status
commands always return their complete set and do not expose pagination flags. `events tail` walks every page back to the
newest event it has already shown, so a burst larger than one page is not skipped.

```bash
airmux orgs list --limit 25 -f json
airmux events list --all -f text
airmux commands -f table
```

`airmux commands` is the source-backed inventory for the installed CLI version.

Top-level help groups commands by task:

| Category | Commands |
| --- | --- |
| Getting started | `quickstart`, `commands` |
| Connection | `login`, `profiles`, `status`, `doctor` |
| Goodies | `completion` |
| Services | `gateway`, `control-plane` |
| Manage resources | Organizations, workspaces, keys, catalog, gateways, policies, and events |

Each command group's help keeps its subcommands in one flat list.

## Getting started and connection commands

| Command                                            | Purpose                                                                                                       |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `quickstart`                                       | Claim or resume an instance, create a workspace and inference key, import provider keys, and verify inference |
| `login`                                            | Sign in through the browser device flow                                                                       |
| `status`                                           | Show active endpoints, organization, workspace, and authentication source                                     |
| `doctor`                                           | Check profile permissions, control-plane access, authentication, and gateway readiness                        |
| `profiles list`, `profiles use`, `profiles remove` | Manage saved deployment and organization contexts                                                             |

## Automation pattern

```bash
export AIRMUX_CONTROL_PLANE_URL='https://llm.example.com'
export AIRMUX_MANAGEMENT_KEY='sk-cp-your-key'
export AIRMUX_ORG_ID='your-org-id'

airmux workspaces list -f json
airmux inference-keys create deployment --workspace production
```

Use a service account and a management key limited to the required scope and permissions. One-time secret output should
be captured by a secret manager and not written to logs.
