Docker Compose runs airmux and Postgres. The CLI is available inside the `app` container.

## Start

Follow the [quickstart](/docs/quickstart) to download the release's Compose file and start the stack:

```bash
docker compose up -d --wait
docker compose exec app airmux quickstart --url http://localhost:8080
```

If you need to customize the deployment see [Customize the runtime YAML](#customize-the-runtime-yaml).

## Configure the public origin

For another local port:

```bash
AIRMUX_PORT=9000
AIRMUX_PUBLIC_URL=http://localhost:9000
```

Set these in `.env` and restart Compose. For a public deployment, terminate TLS at a
reverse proxy and set `AIRMUX_PUBLIC_URL` to the exact HTTPS origin.

Set a URL-safe `POSTGRES_PASSWORD` before the first start of a public installation. Changing the Compose variable later
does not rotate the password already stored by Postgres.

## Customize the runtime YAML

Use this when you need to change the control-plane or data-plane settings in the
[configuration reference](/docs/reference/configuration). Copy the default YAML from your running image:

```bash
mkdir -p airmux-config
docker compose exec -T app cat /app/deploy/docker/airmux.yml > airmux-config/airmux.yml
```

Edit `airmux-config/airmux.yml`. Keep its `/state` paths unless you also provide suitable persistent storage, and keep the control plane and data plane on the same secret store. 

The Compose file mounts `./airmux-config` read-only and any change to `airmux.yml` will be picked up when you restart the stack. If the file is absent or empty, each role uses the YAML bundled in the image. A nonempty invalid YAML file causes startup to fail.

Runtime `${env:...}` references use each container's environment, not values read directly from `.env`. Paths in the
custom YAML resolve relative to `/config`, so use absolute `/state/...` paths for persistent data as the bundled file
does. Compare your custom file with the new image's default YAML when upgrading.

Restart all roles after editing the YAML:

```bash
docker compose down
docker compose up -d --wait
```

`down` keeps the database and state volumes. If startup fails, inspect `docker compose logs migrate taxonomy app`.
To return to the image default, remove `airmux-config/airmux.yml` and run the same two commands. The split Compose
example uses the same directory for its migration, catalog, control-plane, and gateway containers.

## Startup and database changes

`docker compose up` runs the migration job first and the catalog job second. The `app` container starts only after both
jobs succeed. On later runs, migration checks the current schema revision and the catalog job reapplies the definitions
shipped with the selected image. To diagnose a failure:

```bash
docker compose logs migrate taxonomy
```

Restarting the `app` container by itself does not run either job. The container does not use development mode, so the control
plane never changes the database schema or catalog while starting; it refuses to serve when the schema is out of date and
tells you to run the migration command.

## State

| Volume | Contents |
| --- | --- |
| `pgdata` | Postgres data |
| `state` | Runtime management key, provider secrets, gateway identity, bundle cache, and usage outbox |

`docker compose down` preserves both volumes. `docker compose down -v` deletes the complete installation.

<Warning>
  Back up both volumes before an update, and do not use `down -v` unless permanent deletion is intended.
</Warning>

## Upgrade and roll back

Read the target release notes and compare any [custom runtime YAML](#customize-the-runtime-yaml) with the target image's
default. Record the current image digest, stop new traffic, and back up Postgres and `/state` together. The migration
job may change the database schema; an older image cannot safely use a database migrated by a newer release.

Download the Compose file for the target release. Remove any older `AIRMUX_IMAGE` override from `.env`, then replace
the stack:

```bash
docker compose up -d --wait
```

Check `/healthz` and `/readyz` on the public origin, run `docker compose exec app airmux doctor`, and send a buffered
and streaming request. Confirm that the requests appear in usage. If verification fails after migration, stop the new
stack, restore Postgres and `/state` from the same backup, and redeploy the recorded previous release. Do not roll
back only the image against the newer database.

Application processes run as UID `10001`. Docker initializes fresh named volumes from the image's state directories.
Bind mounts and custom paths must be writable by the selected container user.
