---
title: 'Gateway only'
description: 'Install the inference gateway as a Python service with a local taxonomy and no Docker, Postgres, or control plane.'
---

Run the gateway by itself when you want one inference endpoint with translation, streaming, routing, and local policies.
You supply the model taxonomy and inference keys through files. Provider credentials resolve from your environment.

## Install

You need Python 3.13+ and uv. Install the CLI with the gateway runtime:

```bash
uv tool install tokkeeper
```

The installed gateway runs outside the checkout and includes a starter taxonomy.

If your shell cannot find `tokkeeper`, run `uv tool update-shell` and restart the shell.

## Initialize and start

Initialize a directory with the shipped taxonomy:

```bash
tokkeeper gateway init --directory gateway
export OPENAI_API_KEY='your-provider-key'
tokkeeper gateway validate --config gateway/tokkeeper.yml
tokkeeper gateway serve --config gateway/tokkeeper.yml
```

`init` checks taxonomy and adapter validity, creates configuration and a private random inference key, and refuses to overwrite
existing files. Omit `--directory` to initialize the current directory. It copies the shipped taxonomy to `taxonomy.yml` and does not print the key.
Pass `--taxonomy PATH` to reference an existing taxonomy without copying it. Set the provider variable for each provider you use:
`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, and so on. Providers without credentials fail only when selected by a request.

`--config` takes precedence over `TOKKEEPER_CONFIG`, then defaults to `./tokkeeper.yml`. File references resolve relative to the
file containing them, so starting from another directory is safe.

The gateway binds to `127.0.0.1:8080` by default. `--host` and `--port` change the listener.

`validate` checks the configuration, taxonomy, inference keys, adapter support, references, and policy compilation.
It does not contact providers or prove that their credentials work. A real inference request is the final verification.

## Make a request

Use an exact `model_id` from your taxonomy. For the shipped taxonomy:

```bash
export TOKKEEPER_INFERENCE_KEY="$(cat gateway/.tokkeeper/inference.key)"
curl --fail http://127.0.0.1:8080/readyz
curl --fail http://127.0.0.1:8080/inf/v1/chat/completions \
  -H "Authorization: Bearer $TOKKEEPER_INFERENCE_KEY" \
  -H 'Content-Type: application/json' \
  -H 'X-Tokkeeper-Dialect: openai_native' \
  -d '{"model":"openai/gpt-5.4-mini","messages":[{"role":"user","content":"Hello"}]}'
```

Add `"stream": true` to the request body for streaming. OpenAI Chat Completions, OpenAI Responses, Anthropic Messages,
and canonical callers use the same gateway. See the [inference reference](/docs/reference/inference).

## Configuration and taxonomy

`gateway/tokkeeper.yml` selects the local bundle, environment secret store, and usage event sink:

```yaml
data_plane:
  bundle:
    kind: local
    path: bundle.yml
    reload_interval_s: 2
  secrets:
    kind: env
  events:
    kind: devnull
```

The bundle path is relative to this configuration file. `gateway/bundle.yml` contains the keys, taxonomy reference, and policies:

```yaml
keys:
  - ${file:.tokkeeper/inference.key}
taxonomy: taxonomy.yml
rules: []
policies: []
```

The taxonomy path is relative to the bundle file, so starting the service from another directory works. Both planes use
the same taxonomy schema. The file contains `providers` and `models`; pricing, capabilities, parameter support, adapter
overrides, and upstream names are used directly from it. Provider icons are accepted as catalog metadata but do not enter
the inference bundle. Unknown fields and duplicate taxonomy entries are rejected.

For a small custom catalog, `taxonomy` can instead contain those two lists inline. Choose one source: there is no
implicit merge or precedence between an external file and inline definitions. Every model in the selected taxonomy is
available to every local inference key unless restricted by your policies. Use a smaller taxonomy to expose fewer models.

The gateway checks bundle and taxonomy content at the reload interval. A valid edit replaces the active snapshot. Invalid
or missing files are logged while the last good snapshot keeps serving. If no valid snapshot has ever loaded, inference and
`/readyz` return `503`. Restarting requires valid files again; local mode does not persist a separate last-good cache.

You can add plaintext inference tokens to `keys` or use file or environment references. Tokens must start with `sk-inf-`, contain
no whitespace, and be unique. Replacing or removing a key takes effect after reload for new requests. Environment variables
are fixed for a running process; changing an environment-based key or provider credential requires restarting the service.
Keep plaintext key files private and out of version control.

## Run the same configuration in a container

After initialization above, run from the checkout containing `gateway/` and `taxonomy/`:

```bash
docker build --target data-plane -t tokkeeper-gateway:local .
docker run --rm --user "$(id -u):$(id -g)" \
  --mount "type=bind,source=$PWD,target=/config,readonly" \
  -e OPENAI_API_KEY -p 8080:8081 \
  tokkeeper-gateway:local serve --config /config/gateway/tokkeeper.yml --host 0.0.0.0 --port 8081
```

The image entry point is `tokkeeper gateway`, so `validate --config ...` and `serve --help` work as container arguments.
Matching the host user allows it to read the private generated key. The read-only mount preserves the relative taxonomy
reference. Mount any taxonomy stored outside the checkout at the corresponding path as well. No control plane or database
is needed for this configuration.

## Standalone limits

The default `devnull` event sink discards usage events. Standalone mode has no management API, console, or usage history.
All keys share one local organization and workspace, with one environment credential per provider.
