## Publish a release

The root `VERSION` file is the public package version. Publish Release takes the full SHA of the exact source commit to release. That commit must be on `main` and have successful Main CI and Security checks. Its `VERSION` determines the release version. The other workspace projects stay at `0.0.0`.

### Checklist

1. Run **Actions → Prepare Release** on `main`, then merge its pull request
2. Wait for **Main CI** and **Security** to pass
3. Run **Actions → Publish Release** on `main` with the full SHA of the green source commit as its `commit` input; wait for it to finish
4. Check the GitHub release and its Compose file, PyPI package, and GHCR version and `latest` tags

Prepare Release opens a pull request that changes `VERSION`. The source SHA can be that pull request's merge commit or a later fix on `main` with the same version. Publish Release confirms that the source is in `main`'s history and that its version has not already been tagged. It uses the validated Python and container artifacts from that exact source commit's successful Main CI run; later merges into `main` do not change the chosen source. Main CI builds and tests Linux AMD64 and ARM64 images on native runners and combines their digests into one manifest. Release installation and container verification run on both architectures, and the published Compose file pins the combined manifest digest. It checks installation and live providers before creating the tag, then publishes and verifies the package and image. The `release` environment supplies provider credentials and `RELEASE_GITHUB_TOKEN`; PyPI uses its trusted publisher for `release.yml`.

### If a release fails

| Failed stage | Action |
| --- | --- |
| Main CI or Security | Fix the failure on a PR, merge it without changing `VERSION`, then dispatch **Publish Release** with the new green source SHA |
| `prepare` | Confirm the input is the full source SHA on `main`, its version tag is unused, and both main checks passed for that exact SHA; then dispatch **Publish Release** again |
| `installation` or `live-providers` before the tag | Retry transient failures on the original run. To change release code, fix it on a PR, merge it without changing `VERSION`, then dispatch with the new green source SHA |
| After the tag or during publication | Rerun failed jobs on the original **Publish Release** run while its Main CI artifacts are available. Keep the tag on its original commit |
| After PyPI or GHCR publication | Inspect the published version and digest, then rerun failed verification or announcement jobs on the original run. If the source must change, prepare a new version; published package bytes and release tags cannot be replaced |
